# 재무관리 프로그램 2.2 수정 및 적용 안내

## 이번 수정 내용

1. ‘확인할 거래’에서 확정 분류를 자동 선택합니다. 같은 법인·거래처·입출금 방향의 확인완료 내역을 우선 참고하고, 적요·거래처·메모 키워드로 분석합니다. 기존에 저장한 확정 분류는 유지합니다. 판단 근거가 부족하거나 후보가 겹치면 ‘기타’로 선택하며, 담당자가 수정할 수 있습니다. 선택만으로 확인완료가 되지 않고 ‘확인’ 또는 ‘선택 거래 확인완료’를 눌러 저장합니다.
2. ‘입금·지급 예정’에 ‘자금계획서 업로드’ 버튼을 추가했습니다. 업로드 화면에서 과거 자금계획서를 읽어 실제 금액이 있는 입금·지급 일정을 생성합니다. 적용 연월을 바꾸면 일자는 유지합니다. 존재하지 않는 날짜가 생기면 저장하지 않고 안내합니다.
3. 기업·경남·농협·신한의 첨부 양식을 인식합니다. 제목·상단 계좌 안내·빈 행·반복 머리글·합계는 거래로 저장하지 않습니다. 농협의 날짜와 시간은 합쳐서 처리합니다. 잘못된 날짜·금액은 저장 전에 원본 행 번호로 알립니다.
4. 경영 대시보드 금액은 ‘123,456,789원’처럼 세 자리마다 쉼표를 표시합니다. 원 단위를 유지하며 금액을 1,000으로 나누지 않습니다. 그래프 축 숫자에도 쉼표를 표시합니다.

## 기존 사이트에 적용하는 순서

버전 2.1의 사용자·기기 승인 기능이 이미 적용되어 있다면 이번 변경에는 추가 SQL 실행이 필요하지 않습니다. 데이터베이스 구조를 바꾸지 않았습니다. 기존 데이터가 있는 곳에 신규 설치용 INSTALL_ALL.sql을 다시 실행하지 마세요.

1. 관리자 화면의 전체 백업 기능으로 재무자료를 저장하고, 현재 프로그램 폴더도 복사해 보관합니다.
2. GitHub Desktop에서 사용하는 저장소 폴더를 엽니다. ‘Repository’ 메뉴의 ‘Show in Explorer’를 사용하시면 됩니다.
3. 기존 ‘public/config.js’를 별도로 복사합니다. 여기에 현재 사용 중인 Supabase URL과 공개 API 키가 있습니다.
4. 수정본 압축파일을 풉니다. 안쪽 ‘changjin-finance-app’ 폴더 안의 파일과 폴더를 기존 저장소의 같은 위치로 복사합니다. 저장소 안에 프로그램 폴더를 한 겹 더 만드는 방식이 아니라, 기존 ‘public’, ‘netlify’, ‘supabase’ 폴더와 같은 위치에 덮어씁니다.
5. ‘public/config.js’는 3번에서 보관한 기존 파일로 되돌립니다. 배포 파일에 포함된 config.js는 예시값이므로 그대로 사용하면 연결되지 않습니다. 비밀키나 service_role 키를 넣지 마세요.
6. GitHub Desktop에서 변경 내용을 확인하고 ‘Commit to …’를 누른 다음 ‘Push origin’을 누릅니다.
7. Netlify에서 해당 배포가 완료되었는지 확인합니다. 빌드의 게시 폴더는 기존처럼 ‘public’입니다.
8. 웹사이트에서 Ctrl+F5를 눌러 새로고침하고 아래 사용 방법대로 확인합니다.

현재 버전이 2.0이라 사용자 승인 기능까지 아직 적용하지 않았다면 ‘docs/APPROVAL_V21.md’를 먼저 확인하세요. 이 경우에만 기존 제공된 ‘supabase/UPDATE_2_1.sql’ 적용이 필요합니다. 이번 2.2 전용 SQL은 없습니다. ‘email not confirmed’는 별도의 로그인 이메일 확인 상태이므로 이번 엑셀 기능 수정으로 자동 해결되는 항목은 아닙니다.

## 은행자료 업로드

1. ‘은행자료 올리기’를 누릅니다.
2. 대상 법인과 계좌를 선택합니다. 법인을 바꾸면 파일 분석 결과가 지워지므로 다시 파일을 선택합니다.
3. 은행에서 내려받은 원본 .xls 또는 .xlsx 파일을 선택합니다. 이번에 보내주신 네 양식은 제목·합계를 직접 지우지 않아도 됩니다.
4. 미리보기의 거래 건수, 입금·출금 합계를 확인합니다.
5. ‘검토 후 가져오기’를 누릅니다. 가져온 거래는 ‘확인할 거래’에서 분류를 검토합니다.
6. 날짜나 금액 오류가 나오면 표시된 원본 행을 확인합니다. 이 검사에서 실패한 파일은 거래 저장을 시작하지 않습니다.

같은 거래를 같은 계좌로 다시 가져오면 기존 거래는 중복 제외합니다. 기존 버전에서 가져온 첨부 신한 양식의 거래 식별자 102건과 호환됨을 검증했습니다. 이전 업로드가 한국 이외의 시간대에서 처리되었거나 원본의 주요 값·형식을 바꾼 경우에는 중복 여부를 별도로 확인하세요.

한 파일에 인식 가능한 시트가 여러 개 있으면 필요한 시트 하나만 별도 파일로 저장해 업로드하도록 안내합니다. 서로 다른 계좌를 임의로 합치지 않습니다. 다른 은행이나 변경된 양식은 동일한 열 별칭을 쓰면 읽을 수 있으나 모든 은행 양식 지원을 보장하지는 않습니다.

계좌의 현재잔고 기준일보다 오래된 거래 파일은 더 최신의 현재잔고를 덮어쓰지 않습니다. 이 경우 거래는 저장되며, 필요하면 ‘계좌·대출·예금’에서 실제 현재잔고를 직접 확인·수정하세요.

## 확정 분류 자동 선택

- 최근 확인완료 내역 최대 1,000건 안에서 같은 법인·같은 거래처·같은 입출금 방향의 분류가 일치하면 참고합니다.
- 참고할 내역이 없으면 관리자 설정의 분류별 키워드와 보완 키워드로 적요·거래처·메모를 분석합니다.
- 입금 전용 분류를 출금 거래에 추천하지 않습니다. 내부이체는 관련 키워드가 있는 경우에만 후보가 됩니다.
- 자동 선택의 이유를 분류 아래에 표시합니다. 근거가 부족하면 ‘기타’이며, 기타 분류가 없다면 직접 선택하도록 둡니다.
- 확정 분류를 담당자가 수정한 후 확인 저장하면 이후 동일 거래처 추천에 활용됩니다. 기존 저장값은 자동으로 바꾸지 않습니다.
- 외부 유료 AI API나 별도 API 키는 필요하지 않습니다. 키워드·이전 분류를 사용하는 규칙 기반 분석이므로 회계적 판단은 담당자가 검토해야 합니다.

## 과거 자금계획서에서 일정 생성

1. ‘입금·지급 예정’에서 ‘자금계획서 업로드’를 누릅니다.
2. 대상 법인을 확인하고 ‘업로드자료_과거 자금계획서.xlsx’를 선택합니다. 자금계획서에는 대상 계좌 선택이 필요하지 않습니다.
3. 원본은 2025년 11월 계획서입니다. 과거 기록으로 넣으려면 그대로 두고, 다른 월의 계획으로 사용하려면 ‘일정 적용 연월’을 변경합니다. 적용 월을 바꾸면 미리보기 예정일도 바뀝니다.
4. 금액과 일정을 검토하고 ‘제외·확인 사항’을 펼쳐 봅니다. 과거 금액이 미래의 정확한 예상금액이라는 의미는 아니므로 수정이 필요할 수 있습니다.
5. ‘검토 후 가져오기’를 누릅니다. 저장 후 생성한 기간의 일정 목록으로 이동합니다.
6. ‘입금·지급 예정’의 조회 시작일과 종료일을 바꾸면 과거 일정도 다시 볼 수 있습니다.

전월이월은 기존 보유현금이므로 새 입금 일정에 넣지 않습니다. 합계도 별도 거래가 아닙니다. 금액이 비어 있거나 0원인 항목은 생성하지 않습니다. 금액은 있지만 내용이 없는 두 항목은 ‘내용 미기재’로 표시해 누락을 방지합니다. 일자 병합 또는 빈 일자는 앞에서 확인한 일자를 이어받습니다. 첫 일자 없이 금액만 있으면 오류를 안내합니다.

입금·지급 방향은 원본의 수입·지출 칸을 따릅니다. MMT 출금·MMT 이체·타계좌 이체는 실제 내부이체 여부를 검토하고 필요하면 일정 수정에서 ‘계좌이체’로 변경하세요. 문구만으로 모든 이체를 자동 제외하지 않습니다.

같은 파일·법인·적용 월의 재업로드는 기존 일정을 덮어쓰거나 중복 생성하지 않습니다. 원본 파일을 수정해 다시 저장하면 새 파일로 인식하므로, 기존 일정을 먼저 확인하고 수정·삭제 후 처리하세요. 같은 파일로 이미 만든 일정을 편집했다면 재업로드해도 편집값을 유지합니다. 통신 오류로 일부 저장된 경우 같은 파일과 같은 조건으로 재시도할 수 있습니다.

## 검증 범위와 한계

첨부파일 전체 읽기, 금액 합계 대사, 날짜·잘못된 금액 차단, 중복 식별자, 분류 선택, 적용 월 변경, 일정 중복 제외, 원 단위 표시를 확인했습니다. 프로그램 자동검사 19개와 DOM 기반 업로드·저장 흐름 검사를 통과했습니다. 임시 PostgreSQL 호환 환경에서 실제 첨부자료를 변환한 은행 198건과 일정 41건의 저장 및 중복 제외를 확인했습니다.

회사 운영 Supabase 및 Netlify에는 직접 접속하거나 배포하지 않았습니다. 화면 배치는 실제 브라우저에서 시각 검증하지 않았으며 DOM 기능 검증을 수행했습니다. 배포 후 실제 계정으로 업로드·저장·조회 확인이 필요합니다. 원본 은행자료와 실제 계좌번호는 배포 압축파일에 포함하지 않았습니다.
